# 新札マップ（仮称）

## 1. サービス概要

「新札がすぐ必要」なのに、どこで手に入るか分からない——そんな人のためのサービスです。新札を出せる・両替できるATMや銀行窓口の「今使える」情報を、実際に現地で確認したユーザー同士が地図上で共有します。

- **誰の**：冠婚葬祭やお年玉などで、急に新札が必要になった人の
- **どんな課題を**：「どこに行けば新札が手に入るか」が現地に行くまで分からず、何軒も店舗を探し回ってしまう課題を
- **どう解決するか**：現地確認済みの最新スポット情報を地図で共有し、無駄足なく手に入る場所へ導く

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- **いつ**：社会人になり、仕事が忙しい時期。友人の結婚式の前日。
- **どんな状況で**：ご祝儀用の新札を用意し忘れていることに前日になって気づき、昼休みに慌てて職場付近の銀行を数軒回った。しかしATMで新札発行できる所はなく、銀行業界の店頭サービス縮小もあって発行可能な銀行になかなかたどり着けない。Web検索の情報も当てにならず、数軒回った末に地方銀行の支店でやっと新札への両替を完了した。しかも他行サービスのため手数料まで取られた。
- **どんな気持ちになったか**：結婚式に間に合わないかもしれない焦り、限られた昼休みを潰して走り回った徒労感、そして手数料まで取られる理不尽さ。まさに「踏んだり蹴ったり」だった。

### 2-2. なぜそれが「気になった」のか

- **価値観**：本来なら「調べれば分かるはず」の情報が、実際には現地に行くまで分からない——この情報の不透明さに強い違和感を持った。
- **性格**：段取り・効率を重んじるタイプで、避けられたはずの無駄足や余計なコスト（時間・手数料）に納得がいかない。
- **状況**：働いていると平日日中に銀行へ行ける時間が限られる。この時間的制約を自分ごととして痛感していた。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

新札を出せる（両替できる）ATM・銀行窓口が、すぐには見つからない。

### 3-2. 本当に解決したい課題は何か（なぜを3回）

- **なぜ困る？** → 新札を出せるATMや窓口が減っており、どこにあるのか分からないから。
- **なぜ分からないと困る？** → 現地に行くまで新札を出せるか分からず、空振りで何軒も回る羽目になり、時間と手数料を浪費するから。
- **なぜその浪費が問題？** → 冠婚葬祭は日時が決まっていて待ったなし。共働きなどで平日日中に動ける時間が限られる中、「間に合わないリスク」「マナー違反になる不安」に直結するから。

→ **本当に解決したい課題**：新札が必要な人が、限られた時間の中で「確実に手に入る場所」へ最短でたどり着けず、不安と徒労を強いられていること。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

- **年齢**：30代前半
  - 理由：友人の結婚式が集中する年代（20代後半〜30代）で新札が入用になる頻度が高く、かつ働き盛りで平日日中に銀行へ行きにくいため。
- **生活・状況**：共働き・フルタイム勤務。平日は多忙で、銀行窓口の営業時間（〜15時など）に間に合わない。冠婚葬祭が不定期に発生する。
  - 理由：「昼休みや退勤後の短い時間で、今・近くで新札が手に入る場所」を即座に把握できれば、限られた時間でも動ける。
- **環境**：都市部〜地方都市。銀行の統廃合やATM・両替機の縮小が進み、店舗ごとの新札対応がバラバラ。
  - 理由：現地確認済みのユーザー投稿があれば、公式情報では追えない店舗ごとの最新実態を補える。

### 4-2. 自分とユーザーの距離

**過去の自分。** 自分自身がまさにこの状況で数軒を空振りし、時間と手数料を払った実体験があるため、課題の切実さと「これがあったら絶対使った」という感覚をリアルに分かっているから。

### 4-3. 実際に使われる可能性について

- **最初に使ってくれそうな人**：自分と同世代で、冠婚葬祭が多く平日多忙な会社員。
- **思い出す場面**：ご祝儀・お年玉などで「明日までに新札が要る」と気づいた瞬間。
- **今の代替手段**：Web検索、銀行公式サイトの両替機店舗案内、電話問い合わせ、手当たり次第に店舗を回る。
- **置き換えてまで使う理由**：既存手段は「新札が今そこで手に入るか」の現地・最新情報がなく、結局空振りする。現地確認済み情報があれば無駄足を減らせる。

### 4-4. 導入・継続の流れ

- **知る/思い出すきっかけ**：新札が必要になり検索したときにヒット、またはSNS・口コミ。
- **最初の一歩**：地図の閲覧は登録不要ですぐ使える。スポットを投稿するときだけ登録する。
- **使い続ける理由**：冠婚葬祭・お年玉など定期的に需要が発生する。自分が助けられた経験から「次は自分が投稿して貢献したい」という循環が生まれる。情報は溜まるほど便利になる。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- **サービス名**：Googleマップ
  - **URL**：https://www.google.com/maps
  - **できること**：銀行・ATMの位置検索、口コミ閲覧。ただし「新札が出るか／両替できるか」は分からず、口コミにもその情報はほぼ載らない。
- （参考）**各銀行公式の「両替機・両替対応店舗検索」**：自行店舗の両替機有無は分かるが、銀行をまたいだ横断検索や新札発行可否のリアルタイム情報はない。
- （参考）**各行のATM検索アプリ**：ATMの場所は分かるが、新札発行可否には非対応。

### 5-2. それでも自分が作りたい理由

どのサービスも「施設がどこにあるか」までで止まっており、「今そこで新札が実際に手に入るか」が分からない。自分が数軒を空振りしたのは、まさにこの"現地の最新実態"が既存サービスに載っていないから。この一番知りたい情報の欠落に、強い不満とズレを感じた。

### 5-3. 差別化を「体験価値」で表現する

このアプリは、**【明日までに新札が要ると気づいた人】の【焦って店舗を探す瞬間】**を一番助けるアプリ。

- **差別化ポイント**：「施設の場所」ではなく「今そこで新札が手に入るという現地確認済みの事実」を届けることで、空振りせず一発で目的地にたどり着ける体験。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- **行動の変化**：手当たり次第に店舗を回る → 事前に現地確認済みのスポットへ直行する。
- **気持ちの変化**：間に合うか不安・走り回る徒労感 → 見通しが立つ安心。
- **考え方の変化**：新札入手は運と面倒 → みんなで共有すれば解決できる問題。

### 6-2. 価値を一文で表す

**「新札が急に必要になった人が、無駄足なく"今手に入る場所"にたどり着けるようになるサービス」**

## 7. このアプリで実現すること

### MVPで作る機能

- 地図・一覧で新札対応スポットを閲覧（**閲覧は登録不要**）
- スポット投稿（店舗名・場所、対応紙幣種別、最終確認日など）
  - **スポットを登録するときのみ、情報の信頼性確保のためユーザー登録（ログイン）を必須にする**
- スポットの検索・絞り込み（エリア、紙幣の種類）
- 最終確認日の表示（情報の鮮度が分かる）

### 本リリースで作る機能

- 地図の作り込み（Leaflet でピン表示・現在地・周辺検索）
- 「確認できた」報告・いいねによる信頼度スコア
- コメント機能
- 通報・モデレーション（誤情報／荒らし対策）

## 8. このアプリの懸念点とその対策

### 懸念点①：コールドスタート（初期は投稿が0で地図が空）

- **何が問題になりそうか**：投稿が集まるまで地図がスカスカで、価値を感じてもらえない。
- **なぜそう思うか**：ユーザー投稿型サービスに共通の宿命だから。
- **考えている対策**：初期は自分の生活圏に絞り、公開情報（銀行の両替機設置店舗など）を種データとして自分で投入。エリアを狭く濃くして「使える」状態から始める。

### 懸念点②：投稿情報の信頼性

- **何が問題になりそうか**：誤情報・古い情報・荒らしが混じると、空振りが減らず本末転倒になる。
- **考えている対策**：投稿は登録ユーザー限定、最終確認日で鮮度を可視化、「確認できた」報告で裏取り、通報機能で除去。

### 懸念点③：情報の陳腐化

- **何が問題になりそうか**：新札対応は店舗都合で変わるため、情報がすぐ古くなる。
- **考えている対策**：最終確認日を前面に出し、古い情報には再確認を促す導線を作る。

## 9. 今後の展開・発展の方向性

- **使い続ける理由**：冠婚葬祭・季節行事（お年玉など）で定期的に需要が発生する。
- **データが溜まると**：エリアごとの「新札が手に入りやすい場所」の傾向が見えてくる。
- **他の人との関わり**：投稿への感謝や信頼スコアで、貢献が可視化され継続の動機になる。

### 今考えている発展案

- **機能追加の方向性**：両替手数料の有無・両替機の対応時間帯の共有、金融機関情報との連携。
- **UI・体験の改善**：現在地からの近さ・鮮度で並べ替え、「今すぐ手に入る」順の表示。
- **機能以外の工夫**：地域コミュニティや行事シーズンに合わせた情報の呼びかけ。

## 10. 技術スタック

### 10-1. 使用予定の技術

- **フレームワーク**：バックエンド FastAPI (Python 3.12) ／ フロントエンド Next.js 14 (App Router, TypeScript)
- **DB**：PostgreSQL 16（SQLAlchemy 2.0 async / Alembic）
- **デプロイ先**：Render（API）＋ Vercel（フロント）
- **使用予定ライブラリ**：Pydantic v2、Tailwind CSS、shadcn/ui、Leaflet（地図・OpenStreetMap）、pytest、Playwright

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| FastAPI | 採用 | RUNTEQのPythonトラックで一貫して学んだ。型安全・非同期でAPI構築に向く |
| Django | 不採用 | 過去課題で経験したが、今回はAPI＋SPA構成のため軽量なFastAPIを選択 |
| Ruby on Rails | 不採用 | RUNTEQ本流だが、自分はPythonトラックで学習してきたため |
| Next.js | 採用 | 過去のFastAPI課題と同構成で、App Router／型を継続して習熟できる |
| Leaflet + OpenStreetMap | 採用 | OSSで利用料が無料。地図表示に必要十分 |
| Google Maps API | 不採用 | 高機能だが従量課金で個人開発にはコスト懸念 |

- **今回チャレンジしたい点**：地図（Leaflet）表示と、ユーザー投稿の「鮮度・信頼度」の設計。
- **不安な点**：地図・位置情報の実装が未経験で、開発工数の見積りが難しい。

### 10-3. キャッチアップ不足の懸念

地図・位置情報はRUNTEQカリキュラム外の新規要素のため、次の懸念があります。

1. **完成までのハードルが高い**：地図ライブラリのキャッチアップに一定の時間を要する可能性がある。
2. **Issueの見積もりが難しい**：どこまで理解していて何が分からないかが不明瞭だと、開発期間内に収まらないリスクがある。

そこで、**MVPでは地図を最小限（一覧＋簡易表示）に留め、本リリースでLeafletを本格導入する段階的アプローチ**を取ります。地図部分は本リリース前にLeaflet単体でキャッチアップ→技術検証したうえで組み込む形が理想と考えています。
